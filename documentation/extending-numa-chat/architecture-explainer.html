Extending Numa Chat

A comprehensive guide to adding new tools and capabilities to the Numa workspace agent

Architecture Overview

Six systems work together to give Numa its tool capabilities. Each is independently extensible.

The Three-Layer Tool Architecture

Click each layer to expand and see what it contains.

Layer 1: Claude SDK Tools Built-in
▶

Standard Claude tools provided by the SDK: Read, Write, Edit, Bash, Glob, Grep, WebSearch, Task, Skill, etc.

Controlled per agent type via tools, allowed_tools, and disallowed_tools in AgentTypeConfig. These are the foundation all agents share.

💡 You rarely need to modify this layer. It's the baseline capability set that Claude brings out of the box.
Layer 2: MCP Tool Groups Custom
▶

Custom tool groups registered as MCP servers. Each group can be independently enabled/disabled per agent type and feature flag.

numa Platform Tools
KB queries, web search, agents, memories, files. The main Swiss Army knife. Uses single-dispatcher pattern with 7+ operations.
integrations Pipedream
SaaS integrations (Gmail, Slack, Jira, etc.) via cross-account proxy model. Three tools: run_action, configure_props, proxy_request.
connectors OAuth Storage
Google Drive, OneDrive, Dropbox, Synergy. Single dispatcher with status, list, search, download operations.
vault Secrets
Secrets management with mandatory approval flow. list_secrets and request_secret operations.
scripts Code Execution
Sandboxed Python/Bash/Node execution. Runs directly in the MicroVM, no Lambda delegation needed.
Layer 3: Skill Documentation Reference
▶

Markdown files that teach Claude how to use the tools. Not executable -- just context loaded on demand. Includes parameter tables, examples, and best practices.

Skills are stored in plugins/numa/skills/ and selectively copied to /workdir/tools/ based on the agent type's enabled_numa_tools list.

✔ This is the most token-efficient way to teach Claude about complex tools. Load the right context at the right time rather than stuffing everything into the system prompt.

Why This Architecture?

🏷 Feature Flagging
Enable/disable entire tool groups without code changes. Ops not ready for a client? Don't register the MCP server. Simple.
🤖 Agent Specialization
A research agent gets KB + web search but no integrations. A data analysis agent gets code execution but no CRM operations. Same engine, different tools.
🔒 Security Isolation
Tools delegate to Lambdas that hold credentials. The agent never sees OAuth tokens, API keys, or user secrets. Permission boundaries enforced server-side.
⚡ Token Efficiency
One tool with 7 operations (single schema) is cheaper than 7 separate tools (7 schemas). Skills load on demand instead of bloating the system prompt.

MCP Tool Groups

The core mechanism for giving Claude executable capabilities. Each group is a collection of Python functions registered as an MCP server.

The Single-Dispatcher Pattern

All major tools use a single dispatcher function with an operation enum. This is more token-efficient than many separate tools because Claude only needs one tool schema.

Registration Flow

MCP servers are conditionally created in sdk_config.py based on agent type config + feature flags:

# sdk_config.py, lines 516-562 mcp_servers: dict[str, Any] = {} if type_config.enable_scripts_mcp: mcp_servers["scripts"] = create_sdk_mcp_server(tools=[execute_script]) if type_config.enable_integrations_mcp: mcp_servers["integrations"] = create_sdk_mcp_server(tools=[run_action, configure_props, proxy_request]) if type_config.enable_numa_mcp: numa_tools = [numa_tool] if os.environ.get("NUMA_OPS_ENABLED"): numa_tools.append(numa_ops_tool) # Feature-flagged! mcp_servers["numa"] = create_sdk_mcp_server(tools=numa_tools)

Three-Layer Access Control

1
Agent Type Config (developer hard limit) -- allowed_numa_operations restricts which operations this agent type can use. A data analysis agent might only get ["knowledge_base", "web_search"].
2
Feature Flags (deployment-level) -- Environment variables like NUMA_OPS_ENABLED, OAUTH_INTEGRATIONS_ENABLED. Controls per-client availability.
3
Frontend Toggles (user-level) -- NUMA_ENABLED_TOOLS allowlist from chat settings. Users can disable tools they don't want.

Prompting & Skills

MCP tools give Claude the ability. Prompting teaches Claude when and how to use it effectively.

System Prompt Assembly

Lambda Delegation

Most tools delegate their actual work to Lambda functions, isolating permissions and credentials from the agent.

Architecture

Credential Isolation

The agent never sees raw credentials. Two credential sets are managed independently:

NUMA_LOCAL_AWS_*
Local account session credentials, captured before cross-account assume. Used by MCP tools (in-process) for Lambda invocation. Ephemeral session tokens only.
AWS_ACCESS_KEY_ID / SECRET / TOKEN
Cross-account Bedrock credentials. Set in the SDK subprocess environment for Claude's reasoning. MCP tools never read these.
🔒 For user OAuth tokens and API keys (like Pipedream, connectors), the Lambda handles auth directly. The MCP tool passes identifiers (user_sub, external_user_id), not credentials. The Lambda looks up tokens from Secrets Manager or DynamoDB.

When to Use a Lambda vs. Running Directly

Human-in-the-Loop (HITL) Approvals

Users approve or deny tool calls before they execute. Critical for write operations like sending emails, creating tickets, or accessing secrets.

Approval Modes

always
Every tool call requires manual approval. Most restrictive. Good for high-security environments.
non_destructive
Read-only operations auto-approve. Writes require approval. Default for integrations.
never
All operations auto-approve. No approval UI shown. Default for Numa-native tools.

Approval Categories

CategoryWrite OperationsSafe (Auto-Approve)

knowledgeBasesuploadquery, list, download
opscreate_*, update_*, delete_*, add_commentget_*, list_*, search_*

Approval Flow

1
SDK Runner identifies tool call requiring approval based on mode + category
2
Generates approval ID (UUID), stores in NUMA_REQUEST_ID_MAP env var
3
Emits SSE event type="tool_approval" with description, props, request_id to frontend
4
Frontend shows approval card with 90-second countdown timer
5
User clicks Approve/Deny -- decision POSTed to API, written to DynamoDB
6
Lambda polls DynamoDB every 5 seconds for decision
7
Result returned: approved (execute), denied (skip), timeout (report)

Frontend Tool Rendering

How tool calls and results appear in the chat UI. Segment-based architecture with specialized components for each tool type.

Segment Types

inline_tool
Single-line indicator with icon, description text, and optional approval panel. Used for file reads, searches, integrations.
tool_card
Card-based result display. Used for KB results, web search results, data analysis output. Supports specialized renderers.
subagent
Container for Task tool results. Shows sub-agent execution with expandable details.

Adding Custom Rendering

  • Route tool name in getToolSegmentKind() to inline_tool or tool_card
  • Set display text in getInlineToolDisplay() -- extract meaningful info from input
  • Set icon in getToolCategoryAndIcon() -- Bootstrap icon or custom image URL
  • For tool_card results: add renderer in toolRenderers/ and register in UnifiedToolCard.tsx
  • For approval: automatic when approval data is attached to segment

Agent Type Configurations

Different agent types get different tool sets from the same engine. This is what makes tool group splitting valuable.

How Tool Groups Enable Agent Specialization

Resolution Chain

When a chat request arrives, tools are resolved through a layered chain:

1
Agent Type Config -- Loaded from registry by type_id. Sets baseline: which MCP groups enabled, which operations allowed.
2
Agent Instance Config -- Fetched from DynamoDB if agentId provided. Further restricts: specific KBs, specific integrations, approval overrides.
3
Request-Level -- enabledConnections, availableKBs, enabledTools from the chat request itself. Runtime toggles.
4
SDK Config Build -- All layers merged. MCP servers registered, env vars set, skill docs copied, prompt assembled.

Agent Builder UI

The Agent Builder (AgentCreateModal.tsx) exposes tool configuration to users:

Tool Toggles
autoToolsEnabled, webSearchEnabled, createAgentEnabled -- Simple on/off switches for major capabilities.
KB Selection
allowedKnowledgeBases -- Multi-select picker. null = all, empty array = none, array of IDs = specific.
Integration Selection
enabledConnections -- Which SaaS integrations this agent can use. Empty = none.
Approval Modes
approvalModes -- Per-category grid: use default / always / non_destructive / never.

Adding a New Tool: Complete Checklist

Not all steps apply to every tool. Use judgment based on your tool's needs.

Define the MCP Tool

Decision: Add to an existing group (preferred for related ops) or create a new group (for independently feature-flaggable capabilities).

Option A: Add to Existing Group

# In numa_tool.py async def _handle_my_operation(params: dict[str, Any]) -> dict[str, Any]: result = invoke_workspace_tool("my_operation", params) return _ok(json.dumps(result)) # Register handler TOOL_HANDLERS["my_operation"] = _handle_my_operation # Add to enum in input_schema "enum": [..., "my_operation"]

Option B: New Tool Group

# my_tool.py from claude_agent_sdk import tool @tool( name="my_tool", description="Description shown in tool schema", input_schema={...} # name + params + description pattern ) async def my_tool(args): ... # Register in sdk_config.py if type_config.enable_my_tool_mcp: mcp_servers["my_tool"] = create_sdk_mcp_server(tools=[my_tool])

Create the Lambda Handler

Only needed if your tool requires permissions or credentials the agent shouldn't have.

# workspace-chat-tools/lambda_function.py def handle_my_operation(params): # Validate params # Do the work (DynamoDB, S3, external API) # Return result return {"status": "success", "data": {...}} # Register in TOOL_HANDLERS dict TOOL_HANDLERS["my_operation"] = handle_my_operation
⚠ Add security gates: validate allowed_tools, check user_sub, apply fail-closed allowlists.

Write the Skill

# plugins/numa/skills/my-tool/SKILL.md --- name: my-tool description: When to use this tool --- # My Tool Skill ## Operations | Operation | Description | Params | |-----------|-------------|--------| | op1 | Does X | a, b | ## Examples mcp__my_tool__my_tool( name="op1", description="Doing X", params={"a": "value"} )

Then register in the TOOL_USAGE prompt section in prompts.py.

Wire Up HITL Approvals

  • Classify operations as safe (read-only) or write (side effects)
  • Add category to numaToolApprovalMode in Settings.tsx
  • Add category to Agent Builder in AgentCreateModal.tsx
  • Use pop_approval_id(action_key) in your MCP tool
  • Pass request_id and auto_approved in Lambda event
  • Use poll_approval() from tools/approval.py
  • Handle: approved, denied, timeout

Frontend Rendering

  • Route tool name in getToolSegmentKind()
  • Set display text in getInlineToolDisplay()
  • Set icon in getToolCategoryAndIcon()
  • Optionally: custom result renderer in toolRenderers/
  • Approval panel renders automatically when approval data attached

Agent Type Configuration

  • Add enable_my_tool_mcp flag to AgentTypeConfig (if new group)
  • Update existing agent types: enable for numa-chat, disable for restricted types
  • Add to enabled_numa_tools for types that should get skill docs
  • Update allowed_numa_operations for types that should get the operation

Infrastructure

  • Add Lambda to infra constructs if new
  • Wire environment variables (Lambda name, table names)
  • Add IAM permissions for the Lambda
  • Add DynamoDB tables if needed
  • Add feature flag if the tool should be toggleable per client
  • Package Lambda: cd lambdas && bash package-python-lambda.sh python/my-lambda

Future Direction: Unified CLI

A longer-term consideration for simplifying the tool architecture.

The Idea

Consolidate all tools into a single Numa CLI binary that Claude executes via Bash, with API documentation provided as reference:

# Instead of MCP tools, Claude runs: $ numa kb query --query "leave policy" --intent "find entitlements" $ numa ops create-ticket --project PROJ --title "Fix bug" --type task $ numa integrations run --action gmail-send-email --props '{"to": "alice@..."}' $ numa vault get --secret "api-key" --purpose "needed for API call"

Trade-offs

Advantages
  • Single entry point -- simpler to maintain
  • New operations = new CLI subcommand
  • Reduced prompt tokens (one tool schema)
  • Claude is naturally good at CLI tools
  • Easier testing (run CLI directly)
Challenges
  • Loses granular MCP grouping for agent types
  • Approval flows need different wiring
  • CLI binary distribution adds complexity
  • Loses structured JSON input/output
  • Security hooks harder to enforce
💡 The current MCP approach works well and provides the flexibility needed for agent specialization. The CLI idea is worth exploring as a simplification pass, but would be a significant architectural change. Consider it a "Phase 2" optimization rather than an immediate priority.
