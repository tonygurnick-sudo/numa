# WorkflowMax (by Xero) — Connection & Reauthorization Guide

> Complete setup instructions for connecting Numa to WorkflowMax.
> Auth type: **OAuth 2.0** (authorization_code + refresh_token).
> Goal: enough detail that Numa could automate connector setup via script.
>
> **Scope:** This is the **WorkflowMax 2** generation (`oauth.workflowmax2.com`,
> `account_id` header) — the one our registry points at. It is **not** the retired
> "WorkflowMax by Xero" flow (`login.xero.com` / `identity.xero.com` / `Xero-tenant-id` /
> `api.xero.com/workflowmax/3.0`). Do not mix the two. See `02-api-spec-investigation.md` §
> "two API generations".
>
> **Confidence:** medium — no live OAuth round-trip was made. Endpoints/scopes are
> `[DOCUMENTED]` from the vendor auth article and the official WorkflowMax 2 authorize
> example; token lifetime figures conflict (~12–30 min) and the data-call base host is
> `[INFERRED]`.

## Auth Type: OAuth 2.0

WorkflowMax 2 uses the OAuth 2.0 **authorization_code** grant. The connecting user consents
once; Numa stores the resulting tokens and refreshes them automatically. The defining quirk:
the **Org ID is a claim inside the access-token JWT**, and must be replayed as the `account_id`
header on every API call.

---

## 1. Create the OAuth Application

The WorkflowMax 2 API is registered through the **Xero Developer portal** (WorkflowMax shares
Xero's identity platform). Matches the connector's `oauthSetupSteps`.

1. Log in to the Xero Developer portal at `https://developer.xero.com/`.
2. Navigate to **My Apps → New app**.
3. Choose **Web app** as the integration type.
4. Fill in:

   | Field                     | Value                                               | Notes                                                       |
   | ------------------------- | --------------------------------------------------- | ----------------------------------------------------------- |
   | App name                  | `Numa Integration`                                  | Shown on the consent screen                                 |
   | Company / application URL | Your Numa URL (e.g. `https://acme.numa.arcanum.ai`) | —                                                           |
   | OAuth 2.0 redirect URI    | `{frontendBaseUrl}/oauth/callback/{oauthSecretId}`  | Generated by the Numa OAuth wizard — **must match exactly** |

5. Save and copy:
   - **Client ID**: a GUID-style string.
   - **Client Secret**: generate it (**shown once — copy immediately**).

> The connecting WorkflowMax user must have **"Authorise 3rd Party Full Access"** enabled on
> their WorkflowMax staff record, or the consent succeeds but API calls are rejected.
> [DOCUMENTED]

## 2. OAuth Flow

| Property             | Value                                                                                     |
| -------------------- | ----------------------------------------------------------------------------------------- |
| Grant type           | `authorization_code`                                                                      |
| Authorization URL    | `https://oauth.workflowmax2.com/oauth/authorize`                                          |
| Token URL            | `https://oauth.workflowmax2.com/oauth/token`                                              |
| Redirect URI         | `{frontendBaseUrl}/oauth/callback/{oauthSecretId}`                                        |
| Scopes (registry)    | `openid profile email workflowmax`                                                        |
| Scopes (recommended) | `openid profile email workflowmax offline_access` ← **add `offline_access`**              |
| `prompt`             | `consent` (set via registry `extraAuthParams`; forces the consent screen + org selection) |
| PKCE required?       | No (confidential web app — client secret held) — [INFERRED]                               |

> **⚠️ `offline_access` is the single most important field here.** The registry scope string
> currently omits it. The official WorkflowMax 2 authorize example and a community Laravel
> implementation both confirm: _a refresh token is only issued when `offline_access` is granted,
> and access tokens only last ~12–30 min._ Without `offline_access`, every connection dies in
> minutes and forces a full re-consent. **Add `offline_access` to `oauth.scopes` in
> `connectorRegistry.ts` before go-live.** [DOCUMENTED]

#### Authorization Request

```http
GET https://oauth.workflowmax2.com/oauth/authorize?
  response_type=code&
  client_id={CLIENT_ID}&
  redirect_uri={frontendBaseUrl}/oauth/callback/{oauthSecretId}&
  scope=openid%20profile%20email%20workflowmax%20offline_access&
  state={RANDOM_STATE}&
  prompt=consent
```

The user logs in, selects the WorkflowMax org, and consents. WorkflowMax redirects back to the
redirect URI with `?code={AUTH_CODE}&state={STATE}`.

#### Token Exchange

```http
POST https://oauth.workflowmax2.com/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
code={AUTH_CODE}&
redirect_uri={frontendBaseUrl}/oauth/callback/{oauthSecretId}&
client_id={CLIENT_ID}&
client_secret={CLIENT_SECRET}
```

> **Critical:** send the parameters in the **request body** (form-encoded), **not** as headers.
> If the resulting JWT contains no Org ID, the exchange was done with params in the headers.
> [DOCUMENTED]

#### Token Response

```json
{
  "access_token": "eyJ...",
  "token_type": "Bearer",
  "expires_in": 1800,
  "refresh_token": "eyJ...",
  "id_token": "eyJ...",
  "scope": "openid profile email workflowmax offline_access"
}
```

`expires_in` ~ **720–1800 s** (≈12–30 min) — trust whatever the response says and refresh
defensively on 401. The `refresh_token` is only present if `offline_access` was granted.

#### Obtaining the `account_id` (Org ID)

1. Decode the `access_token` JWT (it is a standard JWT — base64url-decode the payload).
2. Read the authenticated org's **Org ID** from the claims.
3. Send that Org ID as the **`account_id` header** on every subsequent API call:

```http
GET https://api.workflowmax2.com/staff.api/list
Authorization: Bearer {ACCESS_TOKEN}
account_id: {ORG_UUID}
Accept: application/json
```

> Numa's connector proxy does this for the agent: it decodes the JWT at token time, stores the
> Org ID with the user secret, and injects the `account_id` header on every `connectors(name="request", …)`.
> The agent never handles tokens or the header.

## 3. Token Refresh

```http
POST https://oauth.workflowmax2.com/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&
refresh_token={REFRESH_TOKEN}&
client_id={CLIENT_ID}&
client_secret={CLIENT_SECRET}
```

| Property                | Value                                                                                          | Confidence                |
| ----------------------- | ---------------------------------------------------------------------------------------------- | ------------------------- |
| Access token lifetime   | ~12–30 min (conflicting sources; both short)                                                   | [DOCUMENTED]              |
| Refresh token lifetime  | Not published — Xero-family refresh tokens are typically ~60 days, rotating                    | [INFERRED]                |
| Refresh token rotation? | Likely yes (Xero identity platform rotates refresh tokens on each refresh — store the new one) | [INFERRED — confirm live] |
| Re-consent required?    | When the refresh token is revoked/expired, or scopes change                                    | [INFERRED]                |

> **If refresh returns a new `refresh_token`, persist it immediately** — the old one is dead
> the moment the response is sent (standard Xero-platform behaviour). Treat refresh-token
> rotation as the default and store whatever comes back. [INFERRED — verify on first refresh]

## 4. Token Revocation

No revocation endpoint is documented for WorkflowMax 2. [UNKNOWN]

To "revoke" in practice: delete the stored tokens on the Numa side, and the user can remove the
connected app from inside WorkflowMax (the user's WorkflowMax org settings → connected apps).
The next API call then fails with 401 and triggers the reconnect path.

---

## 5. Reauthorization Triggers

When to prompt the user to reauthorize:

| Trigger               | Detection                              | Action                                                                               |
| --------------------- | -------------------------------------- | ------------------------------------------------------------------------------------ |
| Access token expired  | 401 response                           | Refresh using the refresh token (needs `offline_access`)                             |
| No refresh token      | No `refresh_token` stored (scope gap)  | **Full re-consent every ~12–30 min** until `offline_access` is added                 |
| Refresh token expired | Refresh returns 401/`invalid_grant`    | Full re-consent flow                                                                 |
| Scopes changed        | Registry `oauth.scopes` edited         | Full re-consent flow (new consent screen)                                            |
| User revoked access   | 401/403 + refresh fails                | Full re-consent flow                                                                 |
| Missing `account_id`  | 401/403 with a valid token             | Not a token issue — proxy must inject the `account_id` header                        |
| No 3rd-party access   | 403 despite valid token + `account_id` | User must enable "Authorise 3rd Party Full Access" on their WorkflowMax staff record |

## Numa Connector Wiring

### Credentials to Store

| Key                   | Type           | Description                                                       |
| --------------------- | -------------- | ----------------------------------------------------------------- |
| Client ID             | company secret | OAuth app client ID (admin-supplied, company-wide)                |
| Client Secret         | company secret | OAuth app client secret (admin-supplied, company-wide)            |
| `access_token`        | user secret    | Short-lived JWT bearer token (per user)                           |
| `refresh_token`       | user secret    | Long-lived refresh token (per user; **only if `offline_access`**) |
| `account_id` (Org ID) | user secret    | Decoded from the access JWT; replayed as the `account_id` header  |

> Company OAuth-client credentials (Client ID/Secret) are stored once by an admin. Each user's
> tokens + Org ID are stored per-user. Disconnecting a user deletes only that user's secret;
> removing the connector (admin) deletes the company secret.

### Test Connection Sequence

```
1. POST {tokenUrl} grant_type=authorization_code   → obtain access_token + refresh_token
2. Decode access_token JWT                          → extract Org ID (account_id)
3. GET /staff.api/list  (or GET /staff)
     Authorization: Bearer {access_token}
     account_id: {org_uuid}
     Accept: application/json
   → expect 200 with a staff list (lowest-risk read; confirms token + account_id + 3rd-party access)
```

### Auto-Reconnect Logic

```
on 401 response:
  if a refresh_token is stored:
    try refresh_token()        # POST {tokenUrl} grant_type=refresh_token
    persist any new refresh_token returned (rotation)
    retry the original call once
    if refresh fails (invalid_grant / 401):
      trigger full re-consent flow
  else:
    # scope gap — offline_access was not granted, so no refresh token exists
    trigger full re-consent flow
    surface: "WorkflowMax session expired — reconnect required (add offline_access scope to avoid this)"

on 403 with valid token + account_id present:
  surface: "Your WorkflowMax user needs 'Authorise 3rd Party Full Access' enabled"

on 403 with token but account_id missing:
  # proxy bug, not a user issue — the account_id header was not injected
```
