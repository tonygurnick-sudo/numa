# WorkflowMax (by Xero) — Connection & Reauthorization Guide

OAuth 2.0 **authorization_code** grant. The user consents once; Numa stores + auto-refreshes tokens. Defining quirk: the **Org ID is a claim inside the access-token JWT**, replayed as the `account_id` header on every API call.

## 1. Create the OAuth Application

Registered through the **Xero Developer portal** (WorkflowMax shares Xero's identity platform). Matches the connector's `oauthSetupSteps`:

1. Log in at `https://developer.xero.com/`.
2. **My Apps → New app.**
3. Choose **Web app**.
4. Fill in:

| Field                     | Value                                               | Notes                                                       |
| ------------------------- | --------------------------------------------------- | ----------------------------------------------------------- |
| App name                  | `Numa Integration`                                  | shown on the consent screen                                 |
| Company / application URL | your Numa URL (e.g. `https://acme.numa.arcanum.ai`) | —                                                           |
| OAuth 2.0 redirect URI    | `{frontendBaseUrl}/oauth/callback/{oauthSecretId}`  | generated by the Numa OAuth wizard — **must match exactly** |

5. Save and copy: **Client ID** (GUID-style) and **Client Secret** (generate — **shown once, copy immediately**).

> The connecting WorkflowMax user must have **"Authorise 3rd Party Full Access"** on their staff record, or consent succeeds but API calls are rejected. [DOCUMENTED]

## 2. OAuth Flow

| Property             | Value                                                                             |
| -------------------- | --------------------------------------------------------------------------------- |
| Grant type           | `authorization_code`                                                              |
| Authorization URL    | `https://oauth.workflowmax2.com/oauth/authorize`                                  |
| Token URL            | `https://oauth.workflowmax2.com/oauth/token`                                      |
| Redirect URI         | `{frontendBaseUrl}/oauth/callback/{oauthSecretId}`                                |
| Scopes (registry)    | `openid profile email workflowmax`                                                |
| Scopes (recommended) | `openid profile email workflowmax offline_access` ← **add `offline_access`**      |
| `prompt`             | `consent` (via registry `extraAuthParams`; forces consent screen + org selection) |
| PKCE                 | No (confidential web app — client secret held) [INFERRED]                         |

> **⚠️ `offline_access` is the single most important field here.** The registry scope string omits it. Official WorkflowMax 2 authorize example + community Laravel impl both confirm: a refresh token is only issued when `offline_access` is granted, and access tokens last ~12-30 min. Without it, every connection dies in minutes and forces a full re-consent. **Add `offline_access` to `oauth.scopes` in `connectorRegistry.ts` before go-live.** [DOCUMENTED]

**Authorization request:**

```http
GET https://oauth.workflowmax2.com/oauth/authorize?response_type=code&client_id={CLIENT_ID}&redirect_uri={frontendBaseUrl}/oauth/callback/{oauthSecretId}&scope=openid%20profile%20email%20workflowmax%20offline_access&state={RANDOM_STATE}&prompt=consent
```

User logs in, selects the org, consents → redirect back with `?code={AUTH_CODE}&state={STATE}`.

**Token exchange** (params in the **request body**, form-encoded — NOT headers; if the resulting JWT has no Org ID, the exchange was done with params as headers [DOCUMENTED]):

```http
POST https://oauth.workflowmax2.com/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code={AUTH_CODE}&redirect_uri={frontendBaseUrl}/oauth/callback/{oauthSecretId}&client_id={CLIENT_ID}&client_secret={CLIENT_SECRET}
```

**Token response:**

```json
{
  "access_token": "eyJ...",
  "token_type": "Bearer",
  "expires_in": 1800,
  "refresh_token": "eyJ...",
  "id_token": "eyJ...",
  "scope": "openid profile email workflowmax offline_access"
}
```

`expires_in` ~720-1800 s (≈12-30 min) — trust whatever the response says, refresh defensively on 401. `refresh_token` is only present if `offline_access` was granted.

**Obtaining `account_id` (Org ID):** (1) base64url-decode the `access_token` JWT payload; (2) read the org's **Org ID** from the claims; (3) send it as the `account_id` header on every call:

```http
GET https://api.workflowmax2.com/staff.api/list
Authorization: Bearer {ACCESS_TOKEN}
account_id: {ORG_UUID}
Accept: application/json
```

> Numa's proxy does this for the agent: decodes the JWT at token time, stores the Org ID with the user secret, injects the `account_id` header on every `connectors(name="request", …)`. The agent never handles tokens or the header.

## 3. Token Refresh

```http
POST https://oauth.workflowmax2.com/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&refresh_token={REFRESH_TOKEN}&client_id={CLIENT_ID}&client_secret={CLIENT_SECRET}
```

| Property                | Value                                                                  | Confidence                |
| ----------------------- | ---------------------------------------------------------------------- | ------------------------- |
| Access token lifetime   | ~12-30 min (conflicting sources; both short)                           | [DOCUMENTED]              |
| Refresh token lifetime  | not published — Xero-family typically ~60 days, rotating               | [INFERRED]                |
| Refresh token rotation? | likely yes (Xero identity rotates on each refresh — store the new one) | [INFERRED — confirm live] |
| Re-consent required?    | when the refresh token is revoked/expired, or scopes change            | [INFERRED]                |

> **If refresh returns a new `refresh_token`, persist it immediately** — the old one dies the moment the response is sent (standard Xero-platform behaviour). Treat rotation as the default. [INFERRED — verify on first refresh]

## 4. Token Revocation

No revocation endpoint documented for WorkflowMax 2 [UNKNOWN]. To "revoke" in practice: delete the stored tokens on the Numa side; the user can remove the connected app from inside WorkflowMax (org settings → connected apps). The next API call then fails with 401 and triggers the reconnect path.

## 5. Reauthorization Triggers

| Trigger               | Detection                              | Action                                                                   |
| --------------------- | -------------------------------------- | ------------------------------------------------------------------------ |
| Access token expired  | 401 response                           | refresh using the refresh token (needs `offline_access`)                 |
| No refresh token      | no `refresh_token` stored (scope gap)  | **full re-consent every ~12-30 min** until `offline_access` added        |
| Refresh token expired | refresh returns 401/`invalid_grant`    | full re-consent flow                                                     |
| Scopes changed        | registry `oauth.scopes` edited         | full re-consent flow (new consent screen)                                |
| User revoked access   | 401/403 + refresh fails                | full re-consent flow                                                     |
| Missing `account_id`  | 401/403 with a valid token             | not a token issue — proxy must inject the `account_id` header            |
| No 3rd-party access   | 403 despite valid token + `account_id` | user must enable "Authorise 3rd Party Full Access" on their staff record |

## Numa Connector Wiring

**Credentials to store:**
| Key | Type | Description |
| --- | --- | --- |
| Client ID | company secret | OAuth app client ID (admin-supplied, company-wide) |
| Client Secret | company secret | OAuth app client secret (admin-supplied, company-wide) |
| `access_token` | user secret | short-lived JWT bearer token (per user) |
| `refresh_token` | user secret | long-lived refresh token (per user; **only if `offline_access`**) |
| `account_id` (Org ID) | user secret | decoded from the access JWT; replayed as the `account_id` header |

> Company OAuth-client credentials (Client ID/Secret) are stored once by an admin; each user's tokens + Org ID are stored per-user. Disconnecting a user deletes only that user's secret; removing the connector (admin) deletes the company secret.

**Test connection sequence:**

```
1. POST {tokenUrl} grant_type=authorization_code   → access_token + refresh_token
2. Decode access_token JWT                          → Org ID (account_id)
3. GET /staff.api/list (or GET /staff)
     Authorization: Bearer {access_token}; account_id: {org_uuid}; Accept: application/json
   → expect 200 + a staff list (lowest-risk read; confirms token + account_id + 3rd-party access)
```

**Auto-reconnect logic:**

```
on 401 response:
  if a refresh_token is stored:
    try refresh_token()        # POST {tokenUrl} grant_type=refresh_token
    persist any new refresh_token returned (rotation)
    retry the original call once
    if refresh fails (invalid_grant / 401): trigger full re-consent flow
  else:                        # scope gap — no refresh token exists
    trigger full re-consent flow
    surface: "WorkflowMax session expired — reconnect required (add offline_access scope to avoid this)"

on 403 with valid token + account_id present:
  surface: "Your WorkflowMax user needs 'Authorise 3rd Party Full Access' enabled"

on 403 with token but account_id missing:
  # proxy bug, not a user issue — the account_id header was not injected
```
