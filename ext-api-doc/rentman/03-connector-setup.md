# Rentman — Connector & Integration Setup

## 1. Product context

|              |                                                                             |
| ------------ | --------------------------------------------------------------------------- |
| Vendor       | Rentman B.V. (`rentman.io`) — rental management for AV/event/production     |
| Product      | projects, equipment scheduling & tracking, crew planning, quoting/invoicing |
| App URL      | per-workspace Rentman web app                                               |
| API base URL | `https://api.rentman.net` (single rolling version; fixed SaaS host, HTTPS)  |
| Rate limits  | 50,000 req/day · 10 req/s · max 20 concurrent (documented)                  |

⚠️ **No webhooks** — polling only (`modified[gte]` + `updateHash`).
⚠️ A Pipedream `rentman` integration also exists in Numa (`integrationsConfig.ts`) but its prebuilt actions are broken per FEAT-209 — this native connector is the workaround. The two **are** linked in `PIPEDREAM_TO_CONNECTOR` (`infra/config/connectors.ts` → `rentman: 'rentman'`, mirrored in the agent's `_PIPEDREAM_TO_CONNECTOR`), so an admin's `preferred_method` choice in the unified Integrations UI arbitrates between the Pipedream and native surfaces for Rentman.

## 2. Auth model — per-user Bearer JWT, no admin credential

Every API call carries one secret header:

```
Authorization: Bearer eyJ0eXAiOiJKV1Qi…      ← injected by the Numa backend
Content-Type: application/json               ← standard; no version or tenant headers exist
```

- Token generated by each user in Rentman: **Configuration → Account → Integrations** → (click **Connect** in the "API" field if deactivated) → **Show token**. Long-lived JWT (10yr new tokens), personalized to the generating user — **API access mirrors that user's Rentman role**; no scopes.
- A **per-user secret in Numa**: pasted into the inline chat credential card on first use (stored as `api_key` in the personal vault). The admin wizard collects **no credential at all**.
- **Regenerating the token in Rentman invalidates the old one immediately** → stored copies 401 → users reconnect via the same chat card (see `04-connection-and-reauth.md`).

## 3. Connector registry entry

File: `numa-frontend/src/Components/DataConnectors/connectorRegistry.ts`

```typescript
{
  id: 'rentman',
  displayName: 'Rentman',
  icon: 'bi-truck',
  description: 'Rental management — projects, equipment, crew planning',
  category: 'Rental Management',
  authType: 'token',
  baseUrl: 'https://api.rentman.net',
  cachingPolicy: CACHING_PRESETS.projectManagement,
  // Workspace API token (Configuration → Account → Integrations → API →
  // Show token), sent as a Bearer token. Note: Rentman also runs a
  // first-party MCP server beta (mcp.rentman.net, OAuth 2.1 + PKCE) —
  // a future second surface once the platform supports generic MCP auth.
  credentialFields: [
    {
      key: 'api_key',
      label: 'dataConnectors.fields.apiToken',
      type: 'password',
      placeholder: 'Paste your Rentman API token',
      required: true,
      helpText: 'dataConnectors.fields.rentmanTokenHint',
    },
  ],
}
```

Notes:

- `authType: 'token'` routes the backend to the **single-token Bearer** credential path (same as Fergus/Workbench/GoHighLevel), with the JWT in the `api_key` vault field — the first key `_user_connector_token` looks for.
- No `adminFields`, no `apiKeyHeader`, no `credentialHeaderMap` — plain per-user Bearer.
- No `rateLimitRpm`/`rateLimitDaily` defaults in the registry; the documented budget (10 rps ≈ 600 rpm, 50k/day) can be entered as wizard overrides if throttling shows up.
- `helpText` i18n key (`rentmanTokenHint`, `locales/en/integrations.json`): _"Workspace API token from Rentman → Configuration → Account → Integrations → API → Show token. The token carries full workspace API access."_
- The slug is in `infra/config/connectors.ts` → `NATIVE_CONNECTORS` (under "Rental / field service"), feeding the unified Integrations catalog endpoint, and mirrored in `_NATIVE_CONNECTOR_SLUGS` (`lambdas/python/workspace-chat-tools/tools/user_profile.py`) for `integration:rentman` memory scoping.

## 4. Admin setup (Integrations → Rentman)

Generic `ApiKeyWizard` (`wizards/ApiKeyWizard.tsx`):

1. Open **Integrations**, pick **Rentman**, start the wizard.
2. Step 1 (overview): per-user notice — _no credential is needed here_; each user is asked for their own token the first time they use the connector from chat.
3. Step 2 (review & save) — metadata only. **Leave Instance URL empty** (fixed-host SaaS; the registry `baseUrl` is used). Optional: override display name/icon/description or rate limits.
4. Save → step 3 confirms. No credentials collected anywhere in this flow.

### 4.1 What gets stored — company secret `connector-config-rentman`

The wizard persists a single company vault secret (category "Connector Config"):
| Field | Value |
| --- | --- |
| `display_name` | `Rentman` (or admin override) |
| `icon`, `description` | registry defaults / admin overrides |
| `connector_type` | `token` |
| `base_url` | `https://api.rentman.net` — written from the registry when no instance URL is entered (an admin-entered `instance_url` would take precedence) |
| `credential_fields` | JSON snapshot of the per-user field (`api_key`, password type, "Paste your Rentman API token" placeholder) — drives the inline chat credential card |

No `api_key`/`api_key_header` (no admin credential or static account header) and no `credential_header_map`. Re-running the wizard updates this same secret; a legacy `connector-rentman` **company** secret, if present, is migrated and deleted on save (the per-user `connector-rentman` secrets in personal vaults are untouched).

### 4.2 Prerequisite on the Rentman side

None beyond user access: each connecting user needs a Rentman login whose **role** covers the data they expect to query — the API enforces the generating user's permissions on every call. No app registration, no scope selection, no admin-issued shared credential. (A shared service-account token is possible but trades away per-user permission fidelity.)

## 5. Backend request flow (oauth-workspace-tools)

File: `lambdas/python/oauth-workspace-tools/tools/connect_tools.py`

The agent calls `connectors(name="request", params={connector:"rentman", url:"/projects?limit=50", method:"GET"})`. `handle_connect_request` then:

1. Expands the relative URL against the stored `base_url` (`_resolve_connector_base_url` reads `connector-config-rentman` → `https://api.rentman.net` + `/projects?limit=50`).
2. Looks for an OAuth token (none), then finds the per-user token via **`_user_connector_token`** — the user's `connector-rentman` personal-vault secret, first populated of `api_key`/`bearer_token`/`access_token`/`token` — and builds `Authorization: Bearer eyJ…` (default `Bearer` scheme; no `_auth_header_scheme` override).
3. `_connector_static_headers` contributes nothing (no account-level header on the config); any agent-supplied `headers` are merged last. Rentman needs none.
4. No stored user credential → returns the structured `needs_credential` error (`_needs_credential_response`), surfaced as the **inline chat credential card** built from the `credential_fields` snapshot. On submit, the token is written to the user's personal vault (`connector-rentman`, field `api_key`) via the PAT credentials endpoint (`POST /api/pat/rentman/credentials`), and the request retries.

The agent must **never** set the `Authorization` header itself — the backend injects it and the agent never sees the token. No other Rentman-specific headers exist.

## 6. Smoke test after setup

```http
GET https://api.rentman.net/projects?limit=1&fields=id,name,number
→ 200 with { "data": [...], "itemCount": 1, ... }   — token valid, envelope confirmed
→ 401                                                — token invalid/regenerated → re-enter via chat card
→ 404/empty on known-good data                       — suspect ROLE limits of the generating user
```

From chat: ask the agent to "list my current Rentman projects" — first use triggers the credential card; after the user pastes the token, the request retries and returns projects. Then spot-check the modules the customer cares about (equipment, crew, invoices) to surface role-permission gaps early — and capture one bad-token 401 body for the error-shape record.
