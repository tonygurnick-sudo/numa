Numa CLI

A TypeScript CLI that wraps the Numa platform's tool surface (files, docs, memory, agents, web search, integrations) for dual consumption: by Numa-the-LLM running inside workspace MicroVMs, and by developers running locally to test or script against a Numa instance.

Audience: This reference is internal to the Arcanum team. It documents the CLI as it currently exists — not external user docs.
This is the per-command reference. For the architecture & design — the identity model, the three numa-cli-api gates (Ops entitlement, the Phase-5 per-agent-type allow-list, HITL approval), the permission model (bypassPermissions vs acceptEdits), the agent-side hooks, the per-command rate limit, Saved Workflows, and render-on-reload — read the canonical doc documentation/numa-cli/README.md. Update that doc when a design decision changes, and regenerate this reference when commands/flags change.

Two packages, two binaries

The CLI is split into two npm packages so the workspace image can install only the production surface. The dev binary is a separate package that depends on the prod one and adds extras on top.

PackageBinaryPurpose
@numa/cli
prod		 numa Production binary. Used by Numa-the-LLM inside the workspace MicroVM. Contains no bypass flags or test runners — they don't exist in the bundle.
@numa/cli-dev
dev only		 numa-dev Developer binary. Depends on @numa/cli and bolts on --d-hum (root) + --yes (per-command) + per-category self-tests + dev-context tools + reference launcher. NEVER install in a workspace MicroVM.
How the dev binary reuses prod commands: @numa/cli-dev imports the createXxxCommand() factories from @numa/cli/commands and composes the same Commander trees as the prod binary — then bolts on its own *Test subcommand under each. numa-dev integrations list goes through exactly the same code path as numa integrations list.
Hermetic security model: when the workspace Docker image runs npm install @numa/cli (not @numa/cli-dev), the dev code physically isn't on disk inside the MicroVM. Numa-the-LLM can't find it, can't node ./numa-dev.js, can't bypass HITL by reaching for the dev binary. The boundary is enforced at the package layer, not at runtime.

Two execution contexts

The CLI behaves differently depending on whether it's running inside a workspace MicroVM or on a developer machine. Both routes share the same code path — only the scoping context resolution differs.

ContextHow resolved
In workspace Detected via NUMA_CONVERSATION_ID env var. Reads NUMA_ENABLED_TOOLS, NUMA_ENABLED_INTEGRATIONS, NUMA_ALLOWED_KBS from the MicroVM environment — the frontend toggle is source of truth. LLM cannot self-elevate.
Local dev Falls back to bootstrap context cache at ~/.config/numa/context-<account>.json. Auto-injects required allowed_tools slugs for the command being invoked — the human typing IS the policy.

Three output modes

Every data-returning command supports three flags. Resolution priority: per-command flag > root flag > NUMA_OUTPUT_MODE env > context default.

FlagDefault whenShape
--prettyTTYHuman-readable tables, status lines, truncated content
--standardNUMA_CONVERSATION_ID set_summary envelope: schema + sample + file path (or inline for < 4 KB)
--jsonnon-TTY, no workspaceRaw passthrough — clean for jq

See Output modes for full details on the envelope shape and file-spill behaviour.

Install / setup

# 1. From the monorepo root — yarn discovers both packages via workspaces
$ yarn install
$ cd numa-cli && yarn build   # topological — @numa/cli first, then @numa/cli-dev

# 2. Symlink both binaries onto your PATH
$ ln -sf "$(pwd)/packages/cli/dist/cli/numa.js"         ~/.local/bin/numa
$ ln -sf "$(pwd)/packages/cli-dev/dist/cli/numa-dev.js" ~/.local/bin/numa-dev

# 3. First-time login
$ numa login nd-labs
Quick tour: numa --help for the prod surface, numa-dev --help for dev extras. Per-category help with numa <cat> --help (e.g. numa integrations --help).
Built on the same workspace-chat-tools, kb_manager, and oauth_workspace_tools Lambdas the chat agent uses. The CLI is a strict superset of what the MCP layer exposes today.

auth

Cognito SRP authentication, profile management, and context bootstrap. No AWS credentials needed — Cognito public API only.

Commands

numa login [account]
SRP login flow. Account from positional arg, NUMA_ACCOUNT env var, or interactive prompt. Triggers a post-login bootstrap automatically.
--verbose include AWS $metadata in errors
numa logout
Clear stored tokens for the active profile.
numa-dev whoami (dev binary only)
Print the active profile's identity claims (sub, email, groups, expiry). Auto-refreshes the access token if expired. Removed from the prod numa binary — inside the workspace the agent already has its identity from env/prompt, and it errors on token decode under workspace-IAM auth. Available on numa-dev for laptop use.
--pretty--standard--json
numa profile [name]
Show or set the active profile. No SRP, no token mutation — just the pointer at ~/.config/numa/profile.
--pretty--standard--json
numa bootstrap
Refresh ~/.config/numa/context-<account>.json from /api/cli/bootstrap. Holds KBs, integrations, enabled_tools, user groups — the source of truth for local scoping.
--pretty--standard--json

Worked example — first-time setup

1

Run login. Account positional or env var:

$ numa login nd-labs
$ # or: NUMA_ACCOUNT=nd-labs numa login
$ # or: numa login   # interactive prompt for account name
2

Enter your Cognito password at the secure prompt. Bootstrap runs automatically and writes context to ~/.config/numa/context-nd-labs.json.

$ numa login nd-labs

✓ logged in as nathan@arcanum.ai
numa: bootstrap saved (~/.config/numa/context-nd-labs.json)
3

Verify with whoami:

$ numa whoami
account  nd-labs
email    nathan@arcanum.ai
sub      f4088468-1051-7091-5229-8f49cc9cf34a
groups   admin
expires  2026-05-26T06:22:16.000Z
4

Switch profiles later without re-logging:

Token storage: ~/.config/numa/tokens-<account>.json. Access tokens auto-refresh via Cognito refresh token (30 days). If refresh expires, the next command prompts you to re-login.

files

Knowledge-base operations (the user-facing surface still calls them "files" / "folders" but backend vocabulary is "KBs"). Mirrors the workspace agent's numa_tool MCP operations 1:1.

Commands

numa files list
List folders (KBs) you have access to. Bootstrap-local — no Lambda call.
numa files show <folder>
List files inside a folder. Includes nested subfolders.
numa files search <query>
RAG query across enabled folders. Defaults to LLM-summarised results; --no-summarise returns raw snippets.
--intent <text>--folder <name|id>--max-results <n>--no-summarise
numa files find <pattern>
Filename-pattern search (glob). For content search use numa files search.
numa files download <folder/file>
Download a file using a presigned S3 URL (bypasses the 30s API Gateway timeout).
-o, --output <path>
numa files download-folder <folder>
Download a whole folder as a zip.
numa files upload <local-path>
Upload a local file into a folder. write
numa files mv <src> <dst>
Move a file between folders (or to a subfolder). write
numa files rename <src> <new-filename>
Rename a file in place (same folder + subpath, new filename only). write
numa files mkdir <folder/path>
Create an empty subfolder inside an existing folder. write
numa files rmdir <folder/path>
Delete a subfolder and everything inside it. destructive
numa files delete <folder/file>
Delete a file from a folder. destructive

docs

Document processing on workspace files (paths under /workdir/...). All three commands need an active conversation_id to construct the S3 path where the file lives.

Local dev gotcha: conversation_id is empty by default outside the workspace. Tools fail server-side with "Missing conversation context". Set one with numa-dev context set --conversation-id <id> and seed a fixture at the right S3 path. See the docs self-test for the pattern.

Commands

numa docs extract <file>
Extract text from a workspace file (PDF, DOCX, images, audio, video). Audio/video auto-route to the transcription pipeline. Returns metadata + workspace path of the extracted text file.
-o, --output <local-path>
numa docs transcribe <file>
Transcribe audio/video to text. Returns text inline (not a workspace path). Large transcripts auto-spill to tmp/numa-cli/ in pretty mode.
--mode <voice|meeting>-o, --output <path>
numa docs convert <file>
Convert between formats. markdown mode: text→PDF via Pandoc + LibreOffice. file mode: direct DOCX↔PDF via LibreOffice.
-f, --format <pdf|docx>--mode <markdown|file>--title <title>

agents

Full CRUD on Numa Agents (custom agent personas with system prompts, integrations, KB access). Uses the same DDB tables as the Agent Builder frontend.

Commands

numa agents list
List agents you own or have access to. Compact table: id | scope | visibility | title.
--scope <personal|company|workspace>--search <text>--title <title>--limit <n>--offset <n>
numa agents show <id>
Full agent detail including systemPrompt, integrations, KB filters, created/updated metadata.
numa agents create <title>
Create a new agent. Prompt body via --prompt or --prompt-file. write
--prompt <text>--prompt-file <path>--description <text>--scope <...>--visibility <...>--agent-type <...>
numa agents update <id>
Update fields on an existing agent. Use patch-prompt for find/replace edits on the system prompt. write
--title--description--visibility--prompt-file--integrations <json>
numa agents patch-prompt <id> <old-text> <new-text>
Find/replace edit on system prompt. Cheap diff without re-uploading the whole prompt. Errors if <old-text> appears more than once (use --replace-all if intended).
--replace-all
numa agents duplicate <id>
Duplicate an agent into your personal library. New id, new ownership.
numa agents delete <id>
Delete an agent. destructive

Worked example — create & iterate on an agent

1

Create with prompt inline:

$ numa agents create "Weekly Summariser" \
    --prompt "You generate weekly summaries from Slack messages..." \
    --description "Monday morning team digest" \
    --visibility company
✓ created agent_x9k2...
2

Or load the prompt from a file (preferred for long prompts):

$ numa agents create "Code Reviewer" --prompt-file ./prompts/reviewer.md
3

Update a specific phrase without re-uploading the whole prompt:

$ numa agents patch-prompt agent_x9k2 \
    "summarise the past 7 days" \

✓ patched 1 occurrence
4

$ numa agents duplicate agent_x9k2

Scope vs visibility: scope = where the agent lives (personal / company / workspace). visibility = who else can see + use it.

Commands

--no-playwright--intent <text>--summarise

integrations

External integrations (Gmail, Slack, Salesforce, etc.) across two methods — Pipedream-backed and native — unified under one command tree. Each slug has exactly one active method per user.

Commands

numa integrations list
List enabled integrations with method tag (pipedream | native).
numa integrations docs <slug>
Show paths to integration reference docs. In-workspace: points at /workdir/tools/integrations/<slug>/ (Pipedream) or /workdir/api-docs/<slug>/ (native). Outside: fetches via API and caches at ~/.cache/numa/integrations/.
--via pipedream|native
numa integrations search <query>
Fuzzy-search Pipedream action names across enabled integrations.
--max <n>
numa integrations pipedream-actions <slug>
List all pre-built Pipedream actions for an integration.
numa integrations pipedream-props <slug> <action-key>
Show the prop schema for a single Pipedream action. In-workspace, reads /workdir/tools/integrations/<slug>/<action>.json directly.
numa integrations pipedream-props-options <slug> <action> <prop> [--<prop> <value> ...]
Resolve dynamic dropdown options for a prop. Wraps pipedream_configure_props. Response varies by prop type: {stringOptions: [...]} for string-typed dropdowns, {options: [{label, value}, ...]} for object-typed. Accepts ad-hoc --<prop> <value> flags for the configured-props set (merged with --configured).
--configured <json>--<prop> <value> (ad-hoc)
numa integrations pipedream-call <slug> <action> [--<prop> <value> ...]
Execute a Pipedream action. HITL-gated server-side; CLI auto-approves locally with terminal prompt. Accepts ad-hoc --<prop> <value> flags (auto-camelized, value-coerced) as syntactic sugar over --props '{...}'. side effects
--<prop> <value> (ad-hoc)--props <json>-m, --user-message <text>--stash-id <id>-y, --yes
numa integrations request <slug> <method> <url> [--<field> <value> ...]
Universal HTTP request — auto-routes to Pipedream proxy or native connector based on the slug's method. Accepts ad-hoc --<field> <value> flags as body fields (merged with --body). Headers stay JSON only — header values often contain : and special chars. side effects
--<field> <value> (ad-hoc body)--body <json>--headers <json>--via pipedream|native-m, --user-message <text>-y, --yes
numa integrations list-files <slug> [--folder-id <id>] [--query <text>]
Browse folders/files from a native file-store connector (Synergy 12d, Google Drive, Gmail, OneDrive, Dropbox). Omit --folder-id for the connector root; Synergy uses job:<id> / folder:<id> ids from a prior listing. Read-only.
--folder-id <id>--query <text>--page-size <n>--page-token <token>-m, --user-message <text>
numa integrations search-files <slug> <query>
Search files/jobs by name in a native file-store connector. Read-only.
--folder-id <id>--page-size <n>--page-token <token>-m, --user-message <text>
numa integrations download-file <slug> <file-id> [-o <path>]
Download a connector file by id. In-workspace it lands under /workdir/uploads/connect-<slug>/; sha256-verified end-to-end. Read-only.
-o, --output <path>-m, --user-message <text>
numa integrations file-info <slug> <file-id>
Detailed metadata for a single file (OAuth providers only — Synergy has no metadata endpoint). Read-only.
-m, --user-message <text>
Three input forms (all four wildcard-shape commands):
  • Ad-hoc flags — --ticket-type-id tt-bug --title "Fix" (kebab→camel, value-coerced)
  • JSON blob — --props '{"ticketTypeId":"tt-bug","title":"Fix"}' (best for nested structures + auth)
  • Mix — JSON blob wins on conflict (most explicit). numa ops additionally supports a positional shortcut for search_* ops.
Applies to: numa ops, integrations pipedream-call, integrations pipedream-props-options, integrations request.

Worked example — send an email via Gmail (full discovery flow)

This is the canonical end-to-end flow. Same shape applies to any Pipedream action.

1

List enabled integrations — confirm gmail is connected:

$ numa integrations list
slug                  method     name
--------------------  ---------  ----
gmail                 pipedream
hubspot               pipedream
...
2

Get the docs index — tells you where the per-action JSONs live:

$ numa integrations docs gmail
Documentation for gmail (pipedream integration)
Source: local cache

Reference files (read directly):
  ~/.cache/numa/integrations/gmail/pipedream/_index.json
3

Browse actions — or search:

$ numa integrations search "send email"
gmail  gmail-send-email
  Send Email
  Send an email from your Google Workspace email account...
4

Inspect the prop schema. Look for required props + dynamic dropdowns:

$ numa integrations pipedream-props gmail gmail-send-email
{
  "name": "Send Email",
  "configurable_props": [
    { "name": "gmail", "type": "app", "app": "gmail" },
    { "name": "to", "type": "string[]" },
    { "name": "subject", "type": "string" },
    { "name": "body", "type": "string" },
    { "name": "fromEmail", "type": "string", "remoteOptions": true },
    ...
  ]
}

"remoteOptions": true = dynamic dropdown — resolve with pipedream-props-options before calling.

5

Resolve fromEmail options (the user's Gmail send-as aliases). Pass auth via ad-hoc flag — same as --configured '{"gmail":{"authProvisionId":"auto"}}' but easier to type:

$ numa integrations pipedream-props-options gmail gmail-send-email fromEmail \
    --gmail '{"authProvisionId":"auto"}'
nathan@arcanum.ai
numa: 1 option(s)
6

Execute the action. Two forms — pick whichever is less typing:

# Form A — ad-hoc flags (cleaner for simple values)
$ numa integrations pipedream-call gmail gmail-send-email \
    --gmail '{"authProvisionId":"auto"}' \
    --to '["alice@example.com"]' \
    --subject "Hi Alice" \
    --body "Sending from numa-cli" \
    --from-email "nathan@arcanum.ai" \
    -m "Send greeting to Alice"

# Form B — single JSON blob (best for nested structures, copy-paste from a schema)
$ numa integrations pipedream-call gmail gmail-send-email \
    --props '{"gmail":{"authProvisionId":"auto"},"to":["alice@example.com"],"subject":"Hi","body":"...","fromEmail":"nathan@arcanum.ai"}' \
    -m "Send greeting to Alice"

? Run gmail-send-email (gmail) — Send greeting to Alice (type "yes") yes
✓ sent

Both forms work — --props wins on key conflict. Kebab-case flag names are auto-camelized (--from-email → fromEmail); string values get coerced ("true" → true, "42" → 42, "[...]"/"{...}" → parsed JSON).

7

Or skip the dropdown discovery entirely and use the universal HTTP request command. Body fields also support ad-hoc flags:

# GET — no body needed
$ numa integrations request gmail GET \
    https://gmail.googleapis.com/gmail/v1/users/me/profile \
    -m "GET my Gmail profile"

# POST with ad-hoc body fields (--name and --email become body {"name":...,"email":...})
$ numa integrations request hubspot POST https://api.hubapi.com/crm/v3/objects/contacts \
    --properties '{"firstname":"Alice","lastname":"Smith","email":"alice@x.com"}' \
    -m "Create contact"
Auto-injection: The CLI auto-injects two things behind the scenes:
  • external_user_id = "<client_name>_<user_sub>" — Pipedream Connect's user-namespacing scheme
  • The integration slug into allowed_tools (local-only — workspace inherits from frontend)
Native vs Pipedream: Native integrations don't expose pre-built actions. For native slugs, use numa integrations request for authenticated HTTP API calls, or the file commands (list-files / search-files / download-file / file-info) to browse a connector's files. Synergy 12d is a file-store connector — use the file commands, not request (its request path is intentionally disabled). The pipedream-* commands error helpfully if you target a native slug. A slug should only ever be enabled via one method at a time (the workspace agent dedupes); if a stale context presents both, docs/request refuse to pick silently — re-run with --via pipedream|native.

ops

Numa Ops — tickets, boards, customers, suppliers, projects, work units, custom fields, statuses. Generic pass-through CLI mirroring the 58 operations of the Ops API. single generic command

Command

numa ops <operation> [--params '<json>'] [-m '<text>']
Generic dispatcher. Sends {tool: "ops_<op>", params: {operation, params, ...}} to the workspace-chat-tools Lambda, which routes any ops_* tool name to the same handler the MCP layer uses today.
--params <json>-m, --user-message <text>-y, --yes--pretty--standard--json

Why one generic command?

The Ops surface has 54 operations. Hand-writing per-op subcommands would be high maintenance for little win — the LLM is shaping JSON either way. The CLI's --help lists all valid operations for discovery, and the early validation step catches typos before a Lambda roundtrip.

Approval model

CategoryOperationsApproval
read get_config, list_boards, get_board, list_tickets, get_ticket, search_tickets, list_comments, get_audit, list_work_units, list_customers, get_customer, list_suppliers, get_supplier, list_projects, get_metrics Auto-approved (no prompt)
write Everything else (create_*, update_*, delete_*, add_comment, upload_attachment, bulk_*) Local terminal prompt (per the user's ops approval policy); server-side gate enforces independently

Display IDs vs UUIDs

Tickets have two identifiers — a human-readable display ID (e.g. BUG-001, TASK-042) and a UUID. The Python bridge auto-resolves display IDs to UUIDs for mutation operations (update_ticket, delete_ticket, add_comment, etc.). Always pass displayId when calling those ops; only use ticketId if you already have the UUID. get_ticket has its own display-id route (/ops/tickets/by-display-id/<id>).

Worked example — create a ticket, comment on it, delete it

1

Look up board IDs + ticket type IDs from the config:

$ numa ops list_boards --json | jq '.boards[] | {id, name}'
$ numa ops get_config --json | jq '.ticketTypes[] | {id, name, prefix}'
2

Create a ticket. boardId + title + ticketTypeId are required; stageId usually needed too:

$ numa ops create_ticket \
    --params '{
      "boardId": "<board-uuid>",
      "title": "Investigate API timeout in scheduled run",
      "ticketTypeId": "tt-bug",
      "description": "Customer reported 504s during overnight scheduled run"
    }' \
    -m "file bug for scheduled-run timeout"

Response contains ticket.displayId (e.g. BUG-099) — capture it for the next steps.

Conventions

Cross-cutting patterns every command follows. Worth a one-time read — internalising these means you can drive any command without reading its --help.

-m / --user-message <text> — REQUIRED on every command

Every CLI invocation that hits the platform must supply a short human-readable caption. The chat UI renders it as:

# Frontend rendering
(tool icon) Numa <category>: <user-message>

For HITL-gated write ops, the same text is used as the approval card body. The LLM should always supply it — it's the only window the user has into what an agent is doing. Missing the flag is an instant error.

# Required everywhere — short-flag alias is `-m`
$ numa files show Personal -m "browsing Personal folder"
$ numa web search "tax law NZ" -m "researching tax law" --summarise
$ numa ops create_ticket --board-id <id> --title "Fix bug" --ticket-type-id tt-bug \
    -m "file bug for failing login flow"

# Missing it = clear error
$ numa files show Personal
error: required option '-m, --user-message <text>' not specified

Renamed from --description in earlier versions — description collided with body fields on commands like create_ticket (which has its own description field).

@file shorthand for JSON-blob options

Every option that takes a JSON blob also accepts @/path/to/file.json to read the JSON from disk. Mirrors curl's convention. Solves the shell-escaping pain when payloads contain HTML, embedded quotes, or deep nesting.

OptionUsed on
--params @file.jsonnuma ops <op>
--props @file.jsonnuma integrations pipedream-call
--configured @file.jsonnuma integrations pipedream-props-options
--body @file.jsonnuma integrations request
--headers @file.jsonnuma integrations request
 
# Without @file — escaping HTML in --params is a nightmare
$ numa ops create_ticket \
    --params '{"boardId":"...","title":"...","description":"<p><strong>Context:</strong>..."}' \
    -m "file ticket"

# With @file — write JSON to disk, reference by path
$ cat > /tmp/ticket.json <<'EOF'
{
  "boardId": "...",
  "title": "Harden workspace sandbox: ctypes/cffi block, IMDS firewall",
  "description": "<p><strong>Context:</strong> Full HTML body here with no escaping pain.</p>..."
}
EOF
$ numa ops create_ticket --params @/tmp/ticket.json -m "file workspace hardening ticket"

Useful pattern when the LLM is composing a long body — write to /tmp, reference with @, no inline JSON wrestling.

Three input forms for op-specific args (mix freely)

Applies to numa ops, integrations pipedream-call, integrations pipedream-props-options, and integrations request:

  1. Positional shortcut — search_* ops only. First positional becomes the search term: 
    $ numa ops search_customers acme -m "find Acme contact"
  2. Ad-hoc --kebab-case flags — auto-camelized (--ticket-type-id → ticketTypeId), value-coerced ("true" → true, "42" → 42, "[...]"/"{...}" → parsed JSON): 
    $ numa ops list_tickets --board-id <uuid> --limit 10 -m "list recent tickets"
  3. JSON blob — best for nested objects or copy-paste from a schema: 
    $ numa ops create_ticket --params @/tmp/ticket.json -m "..."

Conflict resolution: --params JSON wins over ad-hoc flags wins over positional. Most explicit beats least explicit.

Output modes — pretty / standard / json

See the Output modes section for the deep dive. Quick summary: TTY defaults to --pretty; piped output defaults to --json; workspace context defaults to --standard (LLM-friendly envelope with auto-spill for large results).

Default board stage on create_ticket

If you omit stageId/stageName when creating a ticket, the bridge auto-resolves to the board's defaultStageId (set in the board config UI under "Default Location for New Tickets"). No-stage tickets land in the board's configured backlog slot.

# Stage omitted — uses board's default ("New" in the Backlog zone, typically)
$ numa ops create_ticket --board-id <id> --title "Investigate timeout" \
    --ticket-type-id tt-bug -m "file timeout bug"

Wire shape

Every command that hits the dispatcher sends {tool, params, context, id_token, user_message} to POST /api/cli/tools/invoke. numa-cli-api routes to one of three downstream targets (workspace_chat_tools, kb_manager, or oauth_workspace_tools) and forwards user_message both at the event top level and inside params for back-compat with existing approval handlers.

Output modes

Every data-returning command flows through a unified emitter that resolves to one of three modes. Designed so the LLM consumer gets lean envelopes while humans get readable tables — without per-command branching.

The three modes

ModeDefault whenUse case
--prettyTTY Human reading at the terminal. Per-command renderers: tables, status lines, truncated content.
--standardNUMA_CONVERSATION_ID set LLM-friendly envelope. Schema + sample + file path lets the LLM use code (cat/jq) to query large results from disk without bloating context.
--jsonnon-TTY, no workspace Clean passthrough for jq piping in scripts.

Resolution priority

Highest wins:

  1. Per-command flag (e.g. numa files show Personal --json)
  2. Root flag (e.g. numa --json files show Personal) — root preAction stashes choice in NUMA_OUTPUT_MODE
  3. NUMA_OUTPUT_MODE env var (for scripting)
  4. Context default (TTY → pretty, workspace → standard, otherwise → json)

Standard envelope shape

{
  "_summary": {
    "tool":    "user_profile_list_memories",
    "count":   47,                  // largest array in the result
    "size":    "12.3 KB",            // serialised size
    "schema":  { ... },                // structural shape — leaves are type names
    "sample":  { ... },                // truncated arrays (2 each), strings (200ch), depth (8)
    "path":    "./tmp/numa-cli/numa-...", // file path | null if inlined
    "inlined": false
  },
  "result": { ... } | null            // populated iff inlined
}

File spill behaviour

Results > 4 KB serialised auto-dump to a file. The envelope contains schema + a bounded sample; the consumer reads the file when it needs the rest.

ContextSpill location
In workspace (NUMA_CONVERSATION_ID set)/workdir/tmp/numa-cli/numa-<tool>-<ts>.json — MicroVM syncs to S3
Outside workspace./tmp/numa-cli/numa-<tool>-<ts>.json — cwd-relative
OverrideNUMA_CLI_TMP_DIR=<path>

Write failures fall back to inline — never crashes a tool call because a filesystem isn't writable.

Sample bounds

The sample field is bounded to keep the envelope small even on pathological payloads (Gmail messages with base64 body data, etc.):

ConstantValueEffect
SAMPLE_ARRAY_LIMIT2First 2 entries per array
SAMPLE_STRING_LIMIT200 charsLonger strings get ...[truncated, N more chars]
SAMPLE_DEPTH_LIMIT8 levelsDeeper values become "[depth limit]"

Schema is unaffected — only shows type names, no bloat risk.

prettyOrSpill — for wildcard-shape commands

Commands whose response shape is unpredictable (pipedream-call, request, web fetch, docs transcribe) use prettyOrSpill() instead of emitResult(). Same mode resolution, but in pretty mode the result is size-checked and spilled to file when > 4 KB instead of dumped to stdout.

Why both helpers?

Commands with a known shape (memory list, agents list, files list) write per-row renderers in pretty mode — these are always table-sized and never need spilling. Wildcard commands return arbitrary JSON shapes (gmail messages, hubspot records, raw HTTP responses); for these, the pretty renderer is essentially "JSON.stringify and dump", which blows up on big results. prettyOrSpill adds the size check before calling the renderer.

Test framework conventions

  • Step framework: [N/M] step name ... ok|FAIL (duration)
  • Exit 0 on full pass, 1 on any failure
  • Cleanup in finally — artefacts deleted unless --keep-artefacts
  • Each test outputs scope info upfront (account, source, enabled integrations) for debugging

Known gaps

The integrations self-test deliberately avoids commands with real side effects:

  • pipedream-call — would actually run an action (send email, create record). No safe noop universally available.
  • request — same problem; could hit a known idempotent GET but per-account credentials vary.
  • Native connect_request — requires a native integration enabled (nd-labs has none).

The five-to-seven existing steps cover everything that's deterministic-friendly. Manual smoke for write paths after Lambda changes.

$ for cat in files docs memory agents web integrations; do numa-dev $cat test; done

Design & Architecture

How a numa <cat> <cmd> invocation reaches the right downstream Lambda — dispatcher routing, scoping resolution, type discipline, and the HITL story.

Request flow

numa <cmd> (CLI binary, TS) │ │ HTTPS w/ Cognito Bearer ▼ API Gateway /api/cli/tools (nd-labs domain → CloudFront → APIGW) │ ▼ numa-cli-api Lambda (Node, ~/lambdas/node/numa-cli-api) │ ─ extracts auth context (sub, email, groups) │ ─ looks up tool in registry │ ─ routes to one of three downstream targets │ ├─→ workspace_chat_tools (Python) files, docs, memory, agents, web, │ integrations (Pipedream) │ ├─→ kb_manager (Python) files mv/rename/mkdir/rmdir │ └─→ oauth_workspace_tools (Python) integrations (native): connect_request, connect_status

Tool registry routing

Centralised in numa-cli-api/src/tools/registry.ts. Maps tool name → downstream target. Unknown tools fall back to workspace_chat_tools (default).

Per-target event shapes

TargetEvent shapeDispatcher
workspace_chat_tools {tool, params, user_sub, user_email, user_groups, allowed_kbs, allowed_tools, external_user_id, conversation_id, id_token} dispatch-chat-tools.ts
kb_manager Synthetic API Gateway event w/ method + path template dispatch-kb-manager.ts
oauth_workspace_tools {tool, user_sub, conversation_id, params} dispatch-oauth-tools.ts

Auto-injection

The dispatcher auto-injects two things callers shouldn't need to know about:

  • external_user_id = f"{client_name}_{user_sub}" — Pipedream Connect's user-namespacing scheme. Required for any Pipedream tool. Mirrored from how the workspace agent builds it at chat start.
  • user_email + user_groups — used by the agents handler for admin overrides + permission checks.

Scoping resolution (CLI side)

resolveScopingContext(account) in context/resolve.ts resolves the user's allowed_kbs, enabled_tools, enabled_integrations, and conversation_id. Three sources, priority order:

SourceWhenAuth fields
workspace-env NUMA_CONVERSATION_ID set From env vars: NUMA_ENABLED_TOOLS, NUMA_ENABLED_INTEGRATIONS, NUMA_ENABLED_NATIVE_CONNECTORS, NUMA_ALLOWED_KBS, NUMA_ALLOWED_KB_OPERATIONS
dev-context ~/.config/numa/dev-context-<account>.json exists From the file. Set via numa-dev context set --conversation-id ... etc. Used for local testing of workspace-context behaviour.
bootstrap-default Otherwise From ~/.config/numa/context-<account>.json. Full bootstrap response with all admin-enabled tools/integrations/KBs. CLI auto-injects per-tool gates locally.

Tool-gate auto-injection (CLI side)

Server-side handlers require specific keys in event.allowed_tools (memories_tool, create_agent_tool, web_search, integration slug). Two paths:

  • In workspace — pass through NUMA_ENABLED_TOOLS unchanged. The frontend toggle is the source of truth; LLM cannot self-elevate.
  • Locally — auto-inject the relevant key for the command being invoked. The human typing IS the policy.

Type discipline

Discriminated unions in metadata/tool-types.ts:

  • ToolCall — discriminated on tool field, narrows params automatically
  • ToolResult<T> — conditional mapped type, infers result shape from tool name
  • ParamsForTool<T> — same idea for params

Every command uses invokeTool<T>() with the tool name as generic; TypeScript flags mismatched param shapes at compile time.

HITL — write op approval

Every write op goes through gateWriteOp() (commands/actions/_hitl.ts). Whether it gates at all comes from the user's approval policy (never / non_destructive / always, per category) resolved in context/approval.ts:

  • Workspace-IAM — the agent resolves the modes per turn (agent override > user chat-settings > default, incl. per-slug integration overrides) and injects them as NUMA_APPROVAL_MODES. Absent/malformed env fails safe to non_destructive. When approval is needed the CLI emits an SSE approval card and sends a request_id; numa-cli-api creates the DDB record and polls until the user clicks Approve/Deny.
  • Laptop — modes come from the bootstrap context file; gating shows a TTY confirm prompt. --yes skips it.

Integrations consult slug override → integrations category mode; under non_destructive, safety comes from the action schema annotations on disk (readOnlyHint, draft + destructiveHint:false; missing schema fails closed) or GET/HEAD for raw proxy requests. Full design: documentation/numa-cli/README.md §5.
